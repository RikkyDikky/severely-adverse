# Findings

Technical findings from building this project, beyond the headline evaluation numbers in the README.

## A PDF's own metadata predicted a silent extraction bug before any output did

Extracting text from all five source PDFs with pdfplumber, four came out clean. The fifth, SR 15-18, had its footnote markers scrambled with the surrounding text — for example, `"1[FTohoetsneote applicability modifications align with the Board's tailoring rules"` instead of the real text, `"[Footnote 1 - ...] These applicability modifications align with the Board's tailoring rules."`

The corruption was narrow, confined to footnote reference points, not the surrounding body text, but genuine: pdfplumber's default extraction reconstructs reading order from each character's on-page (x, y) position, and in this PDF the footnote marker and body text occupy overlapping bounding boxes, so the default sort interleaves their characters. Checking each PDF's Producer metadata (`pdfinfo`) showed why: four documents were generated directly by the Fed's own publishing tool (PDFlib+PDI); this one had gone through ABBYY FineReader, an OCR/reflow tool, at some point.

pdfplumber's `layout=True` mode (preserves visual column spacing) did not fix it. `use_text_flow=True`, which reads text in the order it's actually stored in the PDF's internal content stream rather than reconstructing it from position, fixed it completely and even surfaced header details (OMB control numbers, page footers) the default extraction had been swallowing. Applied only to this one document — the other four extract cleanly with the default, so there was no reason to change what already worked.

The broader point: "chunk it and embed it" quietly assumes text extraction is reliable, and it isn't uniformly reliable even across superficially identical government PDFs. The same code, run against five documents that all look like generic Fed publications, silently corrupted one of them, distinguishable in advance only by a file-format metadata field most pipelines never check. In a compliance-adjacent context, silently mangled text is a worse failure mode than an outright crash — nothing errors, nothing looks broken, and a downstream chatbot would confidently cite a scrambled reading of a real regulation.

## An LLM-as-judge evaluation can leak its own outside knowledge into what's supposed to be a grounded score

The RAG-triad evaluation (context relevance / faithfulness / answer relevance, each scored by a separate LLM call) included a deliberately out-of-scope question: "What is Basel III's minimum leverage ratio requirement?" — not covered by any of the five source documents.

The system gave a careful answer: it correctly noted the documents don't mention Basel III explicitly, while still surfacing the closest related figures it did find (a 4.0% Tier 1 leverage minimum and 3.0% supplementary leverage ratio minimum), explicitly flagged as distinct from Basel III. The judge still scored answer_relevance at 2/5, reasoning that "a more helpful response would have... provided the Basel III requirement (3% for the Tier 1 leverage ratio)." That reasoning only makes sense if the judge is drawing on its own general training knowledge of what Basel III actually requires, not evaluating whether the answer was justified by the retrieved context — which is what the RAG triad is meant to measure.

This is a different failure mode than the common "RAG systems get penalized for honest refusal" observation. It's not a property of the system being evaluated; it's a property of the judge itself. An LLM-as-judge setup can leak its own training knowledge into what looks like a grounded evaluation, even when explicitly prompted to score only against the provided context. In a compliance-adjacent use case, that's a risk in the opposite direction from hallucination: it means an LLM judge could reward a system for volunteering unverified outside information instead of enforcing "stay within the approved, vetted document set" — exactly the discipline you'd want it to enforce. Practically, it also means a low score from an LLM judge isn't automatically actionable feedback without checking whether the judge's own critique is grounded in the actual task constraints or in its own priors.
